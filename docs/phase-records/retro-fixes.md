## RF-I00-01 — Per-run scratch copies for the corpus gate, cargo-nextest as the gate's test runner (2026-09-26)

- **What/why.** Over waves 1-2, 41 `corpus_gate` runs went red. 28 carried a "leaked dropping" row, every one a `Test/AutoTrans/*` export that the r4133 producer and the port reported alike, so no engine held the handle: the 36 `Test/` cases' recursive snapshots read the concurrently running `Test/AutoTrans/` cases' files without `FILE_SHARE_DELETE`, with Defender scanning on. About 20 carried a 120 s capi timeout. Since this step every (case, producer) run of the corpus gate, and every test binary that part 1 measured writing into `tests/corpus/`, compiles a fresh sparse scratch copy (`harness::scratch::ScratchCopy`, keyed by a 16-hex case digest, or `dss_epri::smoke::Ieee13Copy`), removed within `dss_epri::guard::COPY_REMOVE_ATTEMPTS` x `COPY_REMOVE_PAUSE` (25 x 200 ms) or the case fails naming the producer. Decks with no writing verb are still read in place (measured: 72 targets x 0 tree changes). A scheduler task is one case, and the three guards bracket the copy. Both oracle engines leave the process in the deck's folder after a compile (r4133 `Executive/ExecHelper.pas:752-754`, dss_capi `SetCurrentDSSDir`), so both transports step back before they reply. The gate's test runner is `cargo-nextest` 0.9.146 (`.config/nextest.toml`: `retries = 0`, `fail-fast = false`, no groups, no `default-filter`) plus `cargo test --doc` in each lane, commands 4-5 with `DSS_ORACLE_TIMEOUT_SECS=600`.
